Glossário da Aula 05

🎯
Zero-shot
"Shot" = exemplo. Zero exemplos: o modelo faz a tarefa apenas com a instrução, sem ver nenhum exemplo de como deve ficar o resultado.

Analogia: pedir para alguém fazer algo que nunca viu antes — só com descrição verbal.
👆
One-shot / Few-shot
Um ou poucos exemplos incluídos dentro do prompt. O modelo vê o padrão desejado e replica.

Analogia: mostrar 1 ou 3 exemplos de como você quer a saída antes de pedir o resultado real. "Assim → assim. Agora você faz."
📐
Exemplo representativo
Um exemplo que cobre bem os padrões da tarefa — não é marginal nem óbvio demais.

Analogia: se você quer ensinar o que é "fruta", mostrar maçã + banana + laranja é representativo. Mostrar só maçã pode fazer a pessoa achar que "fruta = vermelha e redonda".
💡 Por que "shot"?
O termo vem do paper "Language Models are Few-Shot Learners" da OpenAI (Brown et al., 2020) — o paper que introduziu o GPT-3. A ideia é que o modelo aprende com poucos exemplos (few shots) no contexto, sem retreinamento.

Zero-shot — como o modelo infere sem exemplos

No zero-shot, você confia que o modelo já viu tantos exemplos daquela tarefa durante o treinamento que consegue fazer sozinho — só com a instrução.

O que o modelo faz internamente

Quando você pede "classifique como positivo ou negativo", o modelo:

1. Reconhece a tarefa ("classificação de sentimento")
2. Ativa padrões do treinamento sobre essa tarefa
3. Gera a resposta no formato mais comum para essa tarefa
⚠️ Problema: "formato mais comum" pode não ser o formato que você quer

Quando zero-shot funciona bem

✅ Tarefas amplamente documentadas na internet: tradução, resumo, resposta a perguntas gerais
✅ Quando o formato de saída é flexível (qualquer resposta razoável serve)
✅ Prototipagem rápida — testar se a tarefa é possível antes de refinar
❌ Tarefas com formato muito específico ou terminologia proprietária
❌ Quando variação de formato quebraria o sistema que vai consumir a saída

Se a tarefa é comum e o formato é flexível: zero-shot. Se a tarefa tem formato específico ou você vai usar o output em código: adicione exemplos.

Como o modelo aprende com exemplos no prompt

O Few-shot não "treina" o modelo permanentemente. Ele fornece padrão de entrada → saída que o modelo replica para o novo input.

🧠 O mecanismo por baixo
Quando o modelo vê os exemplos, ele ativa o mecanismo de atenção para identificar o padrão "input X → output Y". Quanto mais claro e consistente esse padrão nos exemplos, mais precisa a replicação para o novo input.

É como aprender pela observação — ver alguém fazer algo 3 vezes é mais poderoso do que ouvir 10 linhas de explicação verbal.
Estrutura padrão de um prompt few-shot:
[Instrução] Classifique o sentimento como POSITIVO, NEGATIVO ou NEUTRO.

[Exemplo 1] Texto: "Adorei o produto, chegou rápido!" → POSITIVO
[Exemplo 2] Texto: "Veio com defeito, péssima qualidade." → NEGATIVO
[Exemplo 3] Texto: "O produto chegou no prazo." → NEUTRO

[Novo input] Texto: "Comprei ontem, ainda não chegou." → ← modelo completa aqui
💡 O que o modelo aprendeu com os 3 exemplos
Formato da saída (maiúsculas, sem ponto final), as 3 categorias possíveis, o padrão "Texto: X → CATEGORIA", e a tonalidade de cada categoria. Tudo isso em 3 linhas — sem descrever nenhuma dessas regras explicitamente.

Zero-shot vs One-shot vs Few-shot — comparativo direto

Mesma tarefa, mesma pergunta final. Só o número de exemplos muda:

❌ Zero-shot (0 exemplos)
Classifique o sentimento:

"O pacote atrasou mas o produto está ótimo."
Possíveis saídas:
"O sentimento é misto."
"Misto — negativo sobre entrega, positivo sobre produto."
"Sentimento: Ambíguo"
→ 3 formatos diferentes = problema para código que lê a saída
⚠️ One-shot (1 exemplo)
Classifique → POSITIVO, NEGATIVO ou MISTO.

Texto: "Entrega rápida!" → POSITIVO

Texto: "O pacote atrasou mas o produto está ótimo."
Saída esperada: "MISTO"

→ Formato consistente, mas com 1 exemplo o modelo pode não saber distinguir NEGATIVO de MISTO
✅ Few-shot (3 exemplos)
Classifique → POSITIVO, NEGATIVO ou MISTO.

Texto: "Entrega rápida!" → POSITIVO
Texto: "Veio com defeito." → NEGATIVO
Texto: "OK, mas esperava mais." → MISTO

Texto: "O pacote atrasou mas o produto está ótimo."
Saída esperada: "MISTO"

→ Formato correto + modelo viu as 3 categorias em uso = confiança alta

A qualidade dos exemplos importa tanto quanto a quantidade

Exemplo ruim = output ruim. Não basta ter 3 exemplos — eles precisam ser representativos da tarefa real.

❌ Exemplos ruins
Problema: todos positivos óbvios
"Ótimo produto!" → POSITIVO
"Adorei!" → POSITIVO
"Perfeito!" → POSITIVO
O modelo não viu como responder para negativos ou mistos. Vai adivinhar — e provavelmente errar.

Problema: exemplos inconsistentes
"Ótimo!" → positivo
"Péssimo" → NEGATIVO
"Ok" → Neutro
Formatos diferentes (minúscula, maiúscula, capitalizado) — o modelo vai variar o formato na saída.
✅ Exemplos bons
Representativo: cobre as 3 categorias
"Adorei, entrega rápida!" → POSITIVO
"Produto quebrado, péssimo." → NEGATIVO
"Chegou no prazo, nada especial." → NEUTRO
Cada categoria representada. Exemplos realistas (não óbvios demais). Formato idêntico nas 3 saídas.

Bônus: cobrir casos difíceis
"Atrasou mas o produto está ótimo." → MISTO
Se você sabe que casos mistos são comuns, inclua 1 exemplo específico para esse padrão.
📖 Fundamentação — Um exemplo bom resolveu o que instrução nenhuma resolvia
Freed, Jacobs e Rózsa (Chatbots that Work, Manning Publications, 2025) relatam um caso real de construção de chatbot: precisavam que o LLM gerasse fragmentos curtos de frase ("esqueci senha") em vez de frases completas, e testaram várias reformulações de instrução sem sucesso. O que resolveu não foi mais instrução — foi acrescentar um único exemplo do formato desejado como primeiro item da lista. Na definição dos próprios autores, one-shot learning é dar ao modelo um exemplo do que você quer, o que ajuda o modelo a processar o pedido melhor do que qualquer explicação em texto. O exemplo só funcionou porque era representativo do padrão real desejado — o mesmo critério de "qualidade sobre quantidade" que separa os exemplos bons dos ruins nos cards acima.

Quantos exemplos usar?

A relação entre número de exemplos e qualidade não é linear. O ponto ideal depende da complexidade da tarefa.

Nº de exemplosQuando usarCusto (tokens)Melhoria esperada
0 (zero-shot)Tarefa comum, formato flexível, prototipagemMínimoBaseline — pode variar muito
1 (one-shot)Quando zero-shot erra no formatoBaixoFormato consistente, mas categorias podem variar
3–5 (few-shot)Tarefa com múltiplas categorias ou padrão específicoMédioMaior consistência — cobre variações
5–10 (many-shot)Tarefa muito específica ou com muitas categoriasAltoMelhora marginal após 5–7 exemplos para a maioria das tarefas
10+ (excessivo)Raramente necessário — considere fine-tuningMuito altoPode até degradar — muitos tokens de exemplos, pouco espaço para resposta
🔬 Descoberta empírica importante
Estudos mostram que passar de 0 para 1 exemplo dá o maior ganho de qualidade. De 1 para 3 dá o segundo maior ganho. De 3 para 5 já é menor. A partir de 5, o ganho é marginal para a maioria das tarefas com LLMs modernos. Comece com 3 e ajuste se necessário.

Código novo desta aula — for loop e lista de tuplas

Dois conceitos Python que aparecem no código da demo:

Lista de tuplas

# Lista = sequência entre [ ]
# Tupla = par fixo entre ( )
variantes = [
    ("ZERO-SHOT", zero_shot),  # tupla 1
    ("ONE-SHOT",  one_shot),   # tupla 2
    ("FEW-SHOT",  few_shot),   # tupla 3
]
# Cada tupla tem: (nome_da_variante, texto_do_prompt)
💡 Por que agrupar assim?
Ao invés de chamar o modelo 3 vezes manualmente, guardamos as variantes numa lista e o for loop faz as 3 chamadas automaticamente. Menos repetição de código.

For loop com desempacotamento

# O for desempacota cada tupla
for nome, prompt in variantes:
    # 1ª iteração: nome="ZERO-SHOT", prompt=zero_shot
    # 2ª iteração: nome="ONE-SHOT",  prompt=one_shot
    # 3ª iteração: nome="FEW-SHOT",  prompt=few_shot
    print(f"{nome}: ...")

# f-string: coloca o valor da variável dentro do texto
# f"ZERO-SHOT: {resultado}" → "ZERO-SHOT: NEUTRO"
💡 Desempacotamento de tupla
for nome, prompt in variantes pega cada tupla e coloca o 1º valor em nome e o 2º em prompt automaticamente.

Few-shot no mercado — onde isso é usado hoje

Plataformas de Help Desk
Classificação automática de tickets
Sistemas de suporte usam few-shot para classificar automaticamente tickets por urgência, categoria e produto. Exemplos são calibrados por especialistas de cada empresa — cada empresa tem seus próprios 5–10 exemplos representativos.
E-commerces
Análise de avaliações de produtos
Classificação de reviews por categoria de problema (entrega, qualidade, atendimento) usando few-shot. Cada categoria tem 3–5 exemplos representativos dos tipos de reclamação mais comuns naquele e-commerce.
Bancos digitais
Extração de intenção do usuário
Chatbots de banco usam few-shot para classificar a intenção de mensagens: "pagar boleto", "ver extrato", "bloquear cartão". Com exemplos de linguagem natural real dos clientes (não linguagem formal), a precisão aumenta muito.

Armadilhas comuns no Few-shot

ArmadilhaO que aconteceComo evitar
Exemplos tendenciosos Todos os exemplos positivos são sobre entrega rápida → modelo generaliza que "positivo = entrega rápida" Diversificar os exemplos — cobrir diferentes tipos de cada categoria
Formato inconsistente Exemplo 1: "→ positivo" / Exemplo 2: "→ POSITIVO" → modelo vai variar Usar exatamente o mesmo formato em todos os exemplos — mesma pontuação, mesma capitalização
Exemplos óbvios demais "Produto ótimo!" → POSITIVO / "Produto péssimo!" → NEGATIVO → modelo não aprende a lidar com casos ambíguos Incluir pelo menos 1 exemplo ligeiramente ambíguo para cada categoria de borda

Última posição vicia O último exemplo pode influenciar desproporcionalmente a resposta — modelo tende a imitar o mais recente Variar a ordem dos exemplos em diferentes testes. Colocar casos difíceis por último, não por primeiro

Guia de decisão — qual técnica usar

Não existe técnica "melhor". Existe a técnica certa para cada situação:

🎯 Tarefa simples e comum
Use Zero-shot — tradução, resumo, resposta geral. Mais barato e rápido.
📐 Formato específico exigido
Use One-shot — o exemplo calibra o modelo para o formato sem usar muitos tokens.
📊 Múltiplas categorias
Use Few-shot (3–5) — um exemplo por categoria mostra a diferença entre elas.
🏷️ Terminologia proprietária
Use Few-shot com exemplos do seu domínio específico — o modelo aprende o vocabulário da empresa.
🔁 Volume alto (milhares/dia)
Considere Fine-tuning — mais caro de criar mas mais barato por chamada em alta escala. (Aula 04 do 2º semestre)

Síntese da Aula 05

✅
Zero-shot = instrução sem exemplo. Funciona para tarefas comuns com formato flexível. Falha quando o modelo precisa saber exatamente como formatar a saída.
✅
Few-shot = instrução + 3–5 exemplos de input → output. Mostra o padrão em vez de descrever. O modelo replica o formato e a lógica dos exemplos.
✅
A qualidade dos exemplos importa tanto quanto a quantidade. Exemplos tendenciosos ou inconsistentes geram outputs tendenciosos ou inconsistentes. 3 bons exemplos > 10 ruins.
✅
Código novo: lista de tuplas [(nome, valor), ...] e loop for nome, valor in lista que desempacota e itera automaticamente.
✅
Passagem de 0 para 1 exemplo dá o maior ganho. De 1 para 3 dá o segundo maior. A partir de 5, o ganho é marginal para LLMs modernos. Comece com 3.

Perguntas frequentes — Few-shot

PerguntaResposta
"Quantos exemplos são suficientes?"Para a maioria das tarefas com LLMs modernos: 3. De 0→1 é o maior salto. De 1→3 é significativo. De 3→5 é marginal. Ajuste só se os erros persistirem após 3.
"A ordem dos exemplos importa?"Sim, ligeiramente. O modelo tende a dar mais peso ao último exemplo (recency bias). Coloque casos representativos em primeiro e casos de borda por último — ou alterne a ordem entre testes.
"Posso usar exemplos do mundo real (dados reais de clientes)?"Cuidado com a LGPD — dados pessoais de clientes reais não devem ir no prompt sem anonimização. Crie exemplos fictícios mas realistas, ou anonimize completamente antes de usar.
"Few-shot substitui o formato do Componente 4?"Não substitui — complementa. O formato ainda pode ser especificado explicitamente. Os exemplos demonstram o padrão, o formato garante a estrutura. Os dois juntos são mais eficazes que cada um sozinho.

O que vem na Aula 06 — Chain-of-Thought

Você já sabe mostrar exemplos de input → output. A Aula 06 vai mostrar como exibir o raciocínio — não só a resposta.

⚠️ O problema que aparece
LLMs erram em raciocínio matemático e lógico quando respondem direto. O modelo prevê a resposta mais provável — que nem sempre é a correta.

Experimento: pergunte ao Qwen3.6 "Se um fazendeiro tem 17 ovelhas e todas menos 9 morrem, quantas sobram?" sem chain-of-thought.
💡 A solução: "pense passo a passo"
Adicionar "Pense passo a passo antes de responder" ao prompt faz o modelo externalizar o raciocínio — e ao externalizar, ele se corrige.

É a técnica mais poderosa para tarefas que envolvem lógica, matemática, análise de causa raiz e tomada de decisão com múltiplos fatores.
🎯 Para a Aula 06
Traga um problema de raciocínio que você quer testar — pode ser matemático, lógico, análise de cenário, priorização de tarefas. Vamos usar como base para a demo ao vivo com e sem Chain-of-Thought.

frutas = ["maçã", "banana", "laranja"]

Construir exemplos representativos ★★★

Individual ou dupla · 25 minutos · O foco é nos exemplos, não no código

  1. Preencha as 4 lacunas com exemplos de tickets reais para cada categoria: CRÍTICO, ALTO, MÉDIO, BAIXO. Pense em situações que você já viveu como usuário de algum serviço.
  2. Execute o notebook (Shift+Enter em cada célula). Veja se o modelo classificou corretamente o ticket de teste como CRÍTICO.
  3. Teste com outros tickets: troque o texto do ticket final por: "Meu usuário não consegue trocar a senha" e depois "A interface está um pouco lenta às vezes". A classificação foi consistente?
  4. Desafio: Se o modelo errar, analise seus exemplos. São representativos o suficiente? Revise os exemplos e rode novamente.
💡 Exemplos para começar (use como referência)
CRÍTICO: "Banco de dados corrompido, dados de clientes perdidos"
ALTO: "Módulo de checkout com erro para 30% dos usuários"
MÉDIO: "Relatório de vendas não carrega para o usuário X"
BAIXO: "Mudar a cor do botão de salvar para azul"
💡 O segredo dos bons exemplos: use textos que uma pessoa real poderia escrever num ticket de suporte — não óbvios demais, não vagos demais. Se seus exemplos são óbvios ("sistema caiu" → CRÍTICO), o modelo pode confundir casos intermediários.
